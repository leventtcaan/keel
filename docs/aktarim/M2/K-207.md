# K-207 · Besin veritabanı spike'ı — aktarım planı

> Durum: main'de (yalnız doküman) · **aktarılmadı**. Değişen: `plan/kararlar/ADR-008-besin-verisi.md` (güncelleme bölümü).
> Hedef seviye: **3/10** — "Bir veri kaynağını kullanmadan önce neyi doğrularsın?"

## Projede nerede, neden şimdi
Motor kalori tahmini yapmaz; yemek kaydının kalorisi veritabanından gelir (U1). ADR-020'de Levent "yalnız USDA FDC" dedi.
K-208 (eşleme) başlamadan: lisans ne diyor, veri nasıl alınır, barkod var mı, Türk ürünleri var mı?

**Tek koşan örnek:** Cheerios barkodu `00016000275287` → FDC API → `gtinUpc` alanıyla tek kayıt, 100 g'da 359 kcal.
Aynı sorgu "torku" için 0 kayıt.

## Basamaklar
| # | Basamak | Somut örnek | Yer |
|---|---|---|---|
| 0 | Lisans okumak | CC0 = kamu malı, atıf **rica** edilir, zorunlu değil; ODbL = türev veritabanını da paylaşma yükümlülüğü | ADR-008 Karar |
| 1 | "Doğrulandı" ne demek (K6) | resmî sayfadan alıntı + API'den gerçek kayıt; özetleyiciye güvenmemek (alanları ben saydım, kendisi tekrarladı → API ile kontrol) | ADR-008 Güncelleme |
| 2 | API mi toplu indirme mi | API: 1.000 istek/saat, kullanıcının aramaları USDA'ya gider; toplu: kendi DB'mizde, sürümlü | ADR-008 veri yolu |
| 3 | Tek sayı → aralık | FDC 100 g'da tek sayı; aralık bizim miktar belirsizliği modelimizden (K-208) | ADR-008 |
| 4 | Kapsam riski | Türk markaları yok → barkod "bulunamadı" çoğunlukta; ürün kararı Levent'te | DURUM › Riskler, soru 10 |

## Canlı kanıt
- `curl …/foods/search?query=cheerios&dataType=Branded` → `gtinUpc: 00016000275287`, `dataSource: GDSN`, enerji 359 kcal/100 g.
- GTIN ile arama → 1 kayıt. "ulker" → 2 (ABD'ye ithal ayçiçek yağı), "torku"/"tadim" → 0.

## Soru bankası
1. CC0 ile ODbL farkı? → CC0 hiçbir yükümlülük yok; ODbL türev veritabanını aynı lisansla paylaşmayı ister.
2. Neden çalışma anında API çağırmıyoruz? → kullanıcının arama metni dışarı gider (V2 ruhu), hız sınırı, kesinti.
3. FDC tek sayı veriyorsa aralık nereden? → miktarın ne kadar kesin olduğundan (tartıldı mı, tahmin mi) ve kaynak türünden.
