## Projede nerede, neden şimdi
Backend M2'de 38 uç nokta açtı; telefon henüz hiçbirine konuşmuyordu. K-304 (çevrimdışı kuyruk) ve K-305 (Apple ile
giriş) bu istemcinin üstüne kurulur. Sözleşme tek kaynak (K3): `openapi.yaml` → `schema.ts` → istemci. Elle tip yok.

**Tek koşan örnek:** sabah tartı: `api.POST('/v1/weigh-ins', { body: { clientId, measuredAt, kg: 80.4, source } })`.
`source: 'GUESS'` yazılırsa `npm run typecheck` kırmızı (sözleşmede kapalı küme). Gönderilirken ara katman o anki
token'ı okur, `Authorization: Bearer …` ekler; 200/201 → `data`, 4xx → `error` (sözleşmedeki `Error` tipinde).

## Satır satır anlatılacak yerler
- `openapi-fetch` neden: aynı yazarın `openapi-typescript`'iyle (ADR-024 zinciri) birlikte çalışır, tek bağımlılığı var
  (`openapi-typescript-helpers`), `fetch` üstünde ince. Alternatif: elle sarmalayıcı — yol/cevap jenerik tiplerini elle
  yazmak, yani sözleşmeyi ikinci kez yazmak (K3'ün kaçındığı şey).
- `apiBaseUrl()` / `parseBaseUrl(value)` ayrımı: Expo `process.env.EXPO_PUBLIC_API_URL` ifadesini derlemede metinle
  değiştirir; saf fonksiyon test edilebilir, gerçek ortam değişkenine bağlı değil (inceleme notu).
- Açık uç noktalara (`/health`, `/v1/auth/refresh`) da token gider: sunucunun o zincirinde token işlenmez
  (`IdentityConfiguration`), süresi geçmiş token yenilemeyi engellemez (inceleyici doğruladı).

## K-304 için not (inceleyici, kurulu kodda doğruladı)
Yeniden deneme `onResponse`'da yazılırsa cihazda (expo/fetch gövdeyi tüketmez) geçer, Jest'te (Node fetch tüketir)
düşer. Temiz yol: tek uçuşlu yenileme + yeniden deneme `fetch`'i saran bir katmanda, ilk gönderimden önce
`request.clone()`. `onResponse` içinden `fetch` çağırmak `onRequest`'i yeniden çalıştırmaz.
