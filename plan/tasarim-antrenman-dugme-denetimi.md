## 1. "Too heavy? Go lighter" (workout.tooHeavy.*)

- **Where:** a row of the More sheet, workout.tsx:1200 (`workout.tooHeavy.link` = "Too heavy?", label `workout.tooHeavy.label` = "Too heavy? Go lighter"). Handler workout.tsx:1215 -> `askTooHeavy` (1080). The prompt is `LoadNote` (train/LoadNote.tsx) rendered at workout.tsx:1114-1121 (page) and 1339 (rest screen).
- **When offered:** it is NOT count-based. The row exists whenever (a) the move is a planned move (not an "Add a move" extra: `planned === undefined` gives null, workout.tsx:1066), (b) the server sent `lighterLoadKg` for it, and (c) that lighter load is below the weight currently typed (`lighterOffer`, train/calibration.ts:70). So: before any set, after a set, after 1-2 tries, all the same. It disappears once the typed weight is at or under the lighter load. It never appears on bodyweight moves (SessionTable returns NONE), nor on a first-ever move with no target and no history (no load to step from).
- **What it computes (server):** backend/training/SessionTable.java: from = next target load, else last best set; lighter = one region load step (load_increment_upper/lower_kg, H3 B4) under it, rounded to the gym in use (LoadSteps.lighter), or the gym's next load down if none in the step. Sent per planned move as `PlannedExercise.lighterLoadKg` (contract openapi.yaml ~4037; ProgramController.java:511). Phone only compares (calibration.ts:70).
- **Behaviour on tap:** shows `workout.tooHeavy.ask` ("If it feels wrong from the first rep, stop and go lighter.") with two buttons `workout.tooHeavy.use` ("Use 57.5 kg") / `workout.tooHeavy.keep`. "Use" just overwrites the typed load of this row (workout.tsx:1085-1090). The same LoadNote/keys are also used by the separate automatic first-session prompt `workout.calibrate.light` ("That weight is light. Next set ...?").
- **What it writes:** nothing of its own. No flag, no field, no API call. The only trace is that the set is logged with the lighter `loadKg`. `asked/putAway/kept` are React state (workout.tsx:398-400), gone with the screen.
- **Readers:** no reader of a "went lighter" choice exists (there is none to read). Indirect effects only, all through the logged load:
  - Next rows in the session start from the load just lifted (train/workout.ts planExercise, `lifted ?? planned.nextLoadKg`, line ~153).
  - Next session's target: backend/training/SessionProgress.retarget (SessionProgress.java:99-140) reads the work sets at the day's TOP load (NextTargets.session, NextTargets.java:~120). If all sets were lighter, the progression restarts from the lighter load. If only the last set(s) went lighter, fewer sets sit at the top load than planned, and NextTargets.after (line ~63: `session.sets().size() < plannedSets`) then holds the load at the top of the range instead of adding load. So "Too heavy?" on one set silently holds the progression; nothing says so.
  - Weekly decision engine: not read (no code path from the choice).
- **Flags:** (a) the control's output is only a number in a field the user could have typed by hand; the value is the stepper's job and is available through the weight stepper (-) already. It earns its place only as a safety nudge (text) plus a server-rounded "gym-correct" jump. (b) The "one step lighter" is the same step as the load step, so for a user whose gym steps are 2.5 kg the button saves one tap. (c) Copy says "Go lighter" but the action is silent about what happens to the next session (hold).

## 3. Superset (superset.*, train/superset.ts, SupersetLink)

- **How it is made:** More row `superset.link` ("Superset with...", workout.tsx:1204, 1219) shown if the move has candidates (other session moves not already in a group, workout.tsx:1150, 1183). It opens `SupersetLink` (train/SupersetLink.tsx) in the move head: text `superset.choose` ("Back to back with which move?"), one Chip per candidate (`superset.pick`), and a `superset.close` ("Cancel") text button. Choosing calls `linkWith` (workout.tsx:1143): a new local group id (`formed`, a React Map, 223) of [slot of this move, slot of partner]. Once linked, the head shows the line `superset.with` ("Superset with X"), and the More row becomes `superset.unlink` ("Not a superset", sets `unlinked`, 1146).
- **What is stored:** only `NewSet.supersetId` (a uuid made on the phone), put on each work set done while in a group (workout.tsx:456 `group?.[0]`). The contract and ADR-035 say groups are read back from the sets. A group that is linked but has no logged set yet exists only in React state and is lost if the screen is left. "Not a superset" is also local; the group is derived again from the last set of each move (`supersetsInForce`, superset.ts:~25).
- **Rest between members: SKIPPED, correctly.** workout.tsx:481-495: inside a group the partner is picked next (`setPicked(found.next ?? move.id)`), the rest timer starts only when `roundDone && !groupDone && resting`, i.e. after the last member of the round; after any other member `endRest()` is called so no timer or alert runs mid-round (comment: "its alert must not sound mid-round (K-411)"). `nextInGroup` (superset.ts:~45) cycles members, skips members with no sets left, and a one-sided move does both sides before the partner. The rest after the round uses the last member's kind for the band (startRest(move)). This matches how a gym superset works. restSeconds is also null for the non-first members (restSpan cleared at workout.tsx:460, 494), matching the contract text.
- **Readers of supersetId:** workout.tsx:349 (live session, and when the session is reopened), app/workout-edit.tsx:69,151 (edit screen shows "Superset with X"), retired workout-summary.tsx:47,68. Backend: stored and returned only (WorkoutStore.java:186, WorkoutController.java:104-127); engine/progression/TrainingTrend/history: not found. exercise-history.tsx does not show it. Doc comment in superset.ts: "the engine does not know of them".
- **Flags:** the superset has real in-session behaviour (no rest between members, partner auto-picked), which is worth its row. After the workout it is only a label in the edit screen. Nothing in History or end screen says it was a superset.

## 4. Rest timer (K-1214, K-1207, K-411; data/parameters/workout.json rest_*)

- **When it starts:** after a logged work set that is not the move's last set (workout.tsx:474-480); in a superset after the round (control 3). Not after warm-ups, not after a move's last set ("After a move's last set no rest comes up: Next names the next move"), not while paused (togglePause calls endRest, 427-431), and Skip set / Skip move / Swap / Later end any running rest (changeSkips 866, swapTo 939).
- **Screen:** while resting the set card is replaced by `RestPage` (workout.tsx:1308-1342): RestTimer clock counting DOWN (train/RestTimer.tsx), the band line (`workout.rest.band`, "2-3 min"), -15 / +15 buttons (`workout.rest.less/more`; press-and-hold sheet), next set line, Up next. Dock button = `workout.rest.end` "Ready" (workout.tsx:1382). Haptic ticks on the last `rest_tick_last_seconds`, a stronger tick at zero, text `workout.rest.over` ("Go when you are ready"), `workout.rest.past` after the band's top. Background notification `workout.rest.alert.*` at the band's low end, moved with +/-15 (train/restAlert.ts).
- **Range/preference logic:**
  - Recommended: ONE band for every move, rest_seconds_min 120 s, rest_seconds_max 180 s (workout.json). The note says "no source gives a different range for isolation moves [kaynak yok]", so none was invented. Timer counts down from the low end, band is shown, "past" is said after the high end.
  - Custom: per kind (COMPOUND / ISOLATION), one fixed value each, bounds rest_custom_min/max_seconds (Settings > Training > Rest, settings/RestSection.tsx; train/restBand.ts `bandFor`). Phone-only (KV key `train.rest`), cleared at sign-out, "nothing the server or the engine reads" (restBand.ts header).
  - A move with no known kind uses the recommended band. -15/+15 in the session changes that one rest only; the next rest starts from the band again (RestTimer.tsx `adjusted` keyed by `since`) and the adjustment is not recorded or learned.
- **Ready before the countdown ends:** `readyRest` (workout.tsx:131-135) closes the span at the moment of the tap (`readySpan`), so the NEXT logged set carries `restSeconds` = whole seconds from "set logged" to "Ready" (restSecondsOf, train/restRecord.ts), capped by `rest_record_max_seconds` (longer = null). If Ready is never pressed (countdown ran out and the user simply logs), restSeconds = until Log. There is NO marker for "cut short" vs "full": the server cannot tell an early Ready from a full rest, and the target band is not stored with it. Time between Ready and Log is not counted. A rest ended any other way (pause, skip, swap, last set, leaving) is voided: that set has no restSeconds. A move's first set and warm-ups carry none.
- **Stored:** `NewSet.restSeconds` (contract 4482-4491) -> `training.workout_set.rest_seconds` (migration V58, WorkoutStore.java:186-193). Returned as `LoggedSet.restSeconds`.
- **Readers: NONE.** Mobile: restSeconds is written in session.ts:228 and workout.tsx:455 only (other files matching "restSeconds" are the timer length, not the record). Backend: WorkoutStore/WorkoutController store and return it; no engine, progression, status or decision code reads it (grep). The commit message of TrainingTrend says "`restSeconds` kullanılmaz" (not used). The export lists the column (veri-envanteri.json ~361). K-1214's third acceptance item, "learning rule via kural-ekle (RIR, failed set); Levent approval", is NOT built (restRecord.ts header: "the adapting rule is a proposal that waits for the product owner"). K-1214's second item, "sourced range for compound/isolation", is also not delivered: only one band, per-kind custom values.
- **Flags:** the actual-rest recording is write-only data today. The per-kind preference in Settings is real (changes the timer) but the app never shows the user how long they actually rested. Contract text says "(a superset: of the round)" and the code does that.

## 5. Reps in reserve / RIR (workout.rir.*)

- **Where:** a row of chips 0, 1, 2+ under the steppers (train/ActiveSet.tsx:127-137; label `workout.rir.short` "Reps left", last chip `workout.rir.more` "2+"). Choices from workout.json `rir_choices` [0,1,2]; "2+" is logged as 2 (session.ts `rirChoice` 202). Always on the set card, no extra tap.
- **Default is the plan's aim, and it is always sent.** The chip preselected is `planned?.targetRir ?? target_rir_max` (workout.tsx:389). A one-tap Log therefore writes `rir` = the aim even if the user never looked at the row (ActiveSet comment: "what is logged when it is left alone is what the person sees"). Contract says rir is "absent when not given", but this phone always gives it (buildSet, session.ts:224). Consequence: every consumer below treats the aim as a measurement unless the user changed it.
- **Writes:** `NewSet.rir` -> `training.workout_set.rir` (WorkoutStore.java:185).
- **Readers (backend):**
  - **E1RM** (engine/E1rm.java:23-32): no estimate without RIR; reps-to-failure = reps + RIR (Epley). Feeds PersonalRecords/records on Progress, the strength chart (mobile progress/strength.ts:58-78 via train/summary.ts e1rm), history records "Estimated max" (train/history.ts estimatedMax).
  - **Progression / next load** (engine/Progression.java:45-65): RIR does NOT decide the next load or reps. Only effect: if any set's RIR > target_rir_max a reason `closer_to_failure` ("go closer") is added to the explanation. Load/reps come from reps vs the range top (double progression). (NextTargets.session, NextTargets.java:~120, substitutes the planned RIR for a set without one.)
  - **Rack-edge rounding** (NextTargets.java:63-71, 99-112): RIR (reps + RIR via Epley) is used only when the gym's next load is "too far": whether sets are worth the range bottom at the heavier load (worthAt / ceilingReaches). Edge case only.
  - **Progress effort lines** (training/ProgressSummary.java:163-167): `EASIER` = same load and reps as last session with more reps left.
  - **TrainingTrend** (origin/main only, engine/TrainingTrend.java): (1) per-lift session e1RM needs RIR (sets without RIR give none, so lifts with no RIR logged are "not read"); (2) `rirDrift`: at a load and reps done in every one of the last 4 sessions, if the mean RIR fell by >= `rir_drift_poor` (1) AND e1RM is not UP, the lift counts as tired; a majority of tired lifts = Recovery POOR. Training DECLINING/IMPROVING/STABLE comes from the e1RM trend (threshold `e1rm_trend_noise_pct` 3%, 2 sessions vs 2 sessions inside 28 days, at least `trend_min_lifts` 2 compounds). Where it reads, the log OVERRIDES the user's weekly check-in answer (DecisionService.currentCheckIn/checkIn, TrainingStatusReader.trend), and the check-in training question is dropped from the list when the log can read. Only compound lifts of the program, sets logged in-app, not imported, not in rest/lighter weeks or the week after.
  - Mobile: in-session "analysis line" (train/insight.ts moveInsight), first-session calibration (train/calibration.ts: RIR >= calibration_rir_min 2 on a no-target move offers a heavier next set; `workout.calibrate.light`), retired workout-summary.tsx.
- **Flags:** (1) Because the default equals the aim, the RIR-drift fatigue signal can only move if the user actively changes the chip; a user who always one-taps produces constant RIR and TrainingTrend reads no drift. (2) The picker cannot say 3+ (logged as 2), so effort above 2 is invisible to E1rm and the drift. (3) RIR is what lets the engine call a session an e1RM; users who never touch it still get an RIR-based e1RM that is really "aim-based".

## 6. "How was your form?" (workout.form.*) and any feeling/effort question

- **When asked:** only at the end. `onFinish` (workout.tsx:652-665) -> `setFinishing(true)` -> bottom sheet `FinishForm` (train/FinishForm.tsx, workout.tsx:1483-1506). Reached from the More row `workout.finish`, the dock "Finish workout" button, or End > Finish. If moves are left, an alert `workout.finishEarly.*` ("N moves left. Finish now? What you logged is saved.") comes first, once.
- **Writes:** `WorkoutFinish.uncleanExerciseIds` (train/workout.ts:224-232) -> `training.workout.unclean_exercise_ids` (migration V24, WorkoutStore.finish:141) and drives retarget at the same moment (SessionProgress.finish 65-68).
- **Readers:** backend/training/SessionProgress.retarget (SessionProgress.java:99-140, line 130: `!uncleanExerciseIds.contains(planned.exerciseId())` -> `techniqueClean`) -> engine/Progression.next (Progression.java:45-50): unclean = `Hold` with reason `technique_gate` (G6 K-31): no load add and no rep chase; next target = same load, `max(weakest reps, range min)` (NextTargets.after Hold). Not returned to the phone: `Workout` record has no unclean field (WorkoutController.java:116), so the user can never see their past answers.
- **Flags, important:**
  - The question is asked once, after the last set, for all moves together, when the user has forgotten move 1 of 6. A form problem noticed mid-session cannot be marked at the move (no per-move "form was off" control on the set screen).
  - **Inert for several moves it is shown for:** Progression returns `NotTracked` for ISOLATION moves before it looks at form (Progression.java:41-44, `load_progression_compound_only`), so "Not clean" on an isolation move does nothing. Moves outside the program day (Add a move, swapped-in moves) are accepted but "have no target to hold" (contract 4279-4283; retarget loops over `day.exercises()` only). So the form chips are meaningful only for planned compound moves, yet FinishForm lists every worked move.
  - The explanatory copy `workout.form.note` ("A move whose form wasn't clean keeps its weight and reps next time, until it is.") exists in en.json and tr.json but is used nowhere in code (rg `form.note` finds no reader). The user is not told what "Not clean" does.
  - A session closed by the server (SessionAutoClose) or left open gets no answer: "No answer on form was given, so nothing is held" (SessionProgress.java:70-75).
  - There is NO other feeling/effort/RPE/difficulty question at workout end (grep rpe, how hard, rating: none). The weekly check-in (checkIn.question.training "How did training go this week?", checkIn.question.recovery "How are you recovering between sessions?") is the only subjective input and is separate from the workout; with the new TrainingTrend, the set log overrides those answers where it can read.

- **"Weeks plan missed" (TrainingStatuses / DeloadLadder):** `weeksPlanMissed` (TrainingStatuses.java:~100-125) counts Monday weeks back from the week just over with fewer distinct training DAYS than the program's days per week (TrainingStatusReader.status:116 `log.workoutStarts`). A day counts when the workout has at least one non-warm-up set (TrainingLog.workoutStarts, TrainingLog.java:51-58: `set_type <> 'WARM_UP'`). Consequences: skipping sets/moves, finishing early, swapping and adding moves have NO effect on missed weeks. One working set = a full session day. A workout of only skipped moves or only warm-ups = no day (finish() leaves empty, workout.tsx:535-559). DeloadLadder reads it at DeloadLadder.java:56 (`overtraining_missed_plan_weeks`, 2). A week off / declared state is neither kept nor missed. So no skip control can create a "missed week"; only not training the day does.
- **Flag:** Skip set, Skip move and Swap are in-session conveniences with no downstream readers at all (by design, ADR-075 #5: "the engine reads what is not there"). They do earn their space as UI state (the row list needs them) but their result is "no set". Taken's server column is the one clear write-only item. Add a move has real downstream use only as history.

Never sent to the server, not in the program, not exported (listed as "setups" in the phone-only inventory, veri-envanteri.json ~1443/1484). Removed at sign-out (trainData.forget). Lost on a new phone/reinstall. Source: G1 K-38 ("same machine set the same way"), ADR-017.
- **Where shown again:** only on this same screen. `training.setup(` has exactly one caller (exercise.tsx:58). NOT shown on the set screen, the rest screen, Today, history or end screen. The user must open More > How to on the move to see their own "seat 4, pin 3".
- **Flag:** the setup note's whole purpose ("set it the same way every time") is defeated when it is two taps away from the set screen at the moment it is needed and invisible otherwise. Output goes nowhere except back to the same form field. Free-text fields (up to `setup_value_max_chars`), no reader in the engine. If the owner wants it to earn space it should surface on the set screen (e.g. as the line under the move name) or move out.

## 9. History view from the set screen (app/exercise-history.tsx)

- **Reached:** More > History (`history.open`, workout.tsx:1197, 1212) and TodayCard.tsx:192. Route `/exercise-history?exercise=<id>`.
- **Shows:** (a) `history.records` card: for a compound external-load move: Heaviest (load x reps), Estimated max (needs RIR, Epley), and Most reps at each weight (one row per distinct weight, heaviest first); isolation: only "Most reps at <load>" per weight; bodyweight: Most reps; weighted bodyweight: heaviest added + most reps with body alone (train/history.ts recordsOf). Records are derived from the shown sets, never stored. (b) `history.sessions` list, newest first, one Card per session containing the move: date, "Edit" link `sessionEdit.open` (only for a session the server has and has ended -> workout-edit), the session note, every set as "kg x reps · N reps left" (warm-ups muted `history.warmUp`), each set note. Empty text `history.empty`, offline text `history.phoneOnly`, failure `history.loadFailed`.
- **Data:** GET /v1/workouts?from=<today-364d>&to=<today> (trainData.history, trainData.ts:150-155; `history_days` 365, workout.json:243; server limit max-range-days 400), joined with the phone's unsent records (train/history.ts sessionsOf). It downloads EVERY workout with ALL its sets of the last year (all moves) and filters to the move on the phone. No pagination, no cursor.
- **How it grows:** linearly and without bound inside the year: one Card per session with that move (about 100 cards for a move trained twice a week for a year), in a plain ScrollView; no grouping by month, no collapse, no chart, no "load more", no search. The records card grows with every distinct weight ever used (`repsAt`). Everything older than 365 days drops out of both the list and the records (a "Heaviest" record is a record of the last year only). Payload also grows with the whole year's training of all moves. The Progress tab has a separate strength chart (progress/strength.ts) over `evaluation_window_days`.
- **Readers of what it displays:** it is a display screen; the data it shows is read by it only. The only write-through is the Edit link (workout-edit).

## 10. Workout-end screen (app/workout-end.tsx, train/workoutEnd.ts) and Share (app/share.tsx)

- **Reached:** `router.replace('/workout-end?workout=<clientId>')` after a finish with at least one work set (workout.tsx:558); a finish with none says `workout.nothingSaved` and goes back.
- **Shows (all server numbers, U1):** Hero "Workout complete" `workoutEnd.title` and the day name; stat boxes: active minutes (finish minus pause), kg/lb lifted over the working sets with `workoutEnd.change` "+N% vs last time" only when positive (U7), working-set count, and kcal only if an Apple Watch measured it (needs both health consents); `New best` card for every record with "Next: kg x reps" from the program (or `workoutEnd.baseline` for a first session); `workoutEnd.week` "N of M sessions this week" with segments (GET /v1/consistency); protein line (GET /v1/days/{day}/budget) with button `workoutEnd.logMeal`; `workoutEnd.moved` "What moved" card per move vs last time (MovedCard, `summary_moves_shown`); `workoutEnd.worked` muscle map. Server read: GET /v1/workouts/{id}/summary after the queue is drained; if the workout/finish is not on the server yet it says `workoutEnd.pending`, on error `workoutEnd.failed` with `workoutEnd.retry`.
- **Does NOT show:** the user's notes, the form answers, RIR/effort, e1RM ("No e1RM, no badge, no points", file header), supersets, skips, swaps, rest taken.
- **Buttons:** `workoutEnd.share` "Share your workout" (secondary, only when ready, workout-end.tsx:114-115), `workoutEnd.done` "Done" (primary, `router.dismissTo('/train')`, :120), `workoutEnd.logMeal` (inside the protein card, -> /meal), `workoutEnd.retry` (pending/failed only).
- **Share flow (app/share.tsx, src/share/*):** route `/share?workout=<id>`; also reachable from Progress (progress.tsx:164) without a workout. Four stickers made on the phone from server numbers: Workout, PR, Streak ("Weeks on track"), Progress (share/stickers.ts; each only if there is something true to say). Preview is an SVG (react-native-svg) rendered to PNG base64 (`toDataURL`). Background chips: gallery photo/video, camera, dark, "In Instagram". Two buttons: `share.story` "Share to Story" (Instagram Stories sticker layer over the user's photo/video or a dark colour; needs the Facebook App ID and Instagram installed, else falls back to the system sheet with `share.storyFallback`; share/story.ts) and `share.share` "Share" (system share sheet with the PNG: Save, TikTok, More). The PNG is written to the app cache only for the hand-over and removed (share/shareImage.ts withCacheFile; file name `next-call-story-sticker.png`, a legacy product name). Nothing is uploaded by the app; text `share.note`: "Made on this phone. No body weight. Your photo stays yours." Not gated to paid users.
- **Flag:** the end screen's headline stat is kg lifted (volume), while other copy (summary.* "effort, not volume") and the retired summary screen argue against volume. The only effort-related output at the end is therefore the "What moved" card, which is the server's word for changes vs last time.
